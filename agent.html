Agent Anatomy

Part one took apart a single turn. This one takes apart the agent: what it is made of, how its knowledge is layered and loaded only when needed, and what actually happens when you hand it a task and walk away.

← Part 1: How AI Harnesses Work

You already know the loop: the harness assembles a context window, calls the model, executes any tool the model asks for, appends the result and goes round again. An agent is that loop plus everything that decides what goes into the context in the first place — an identity, a tiered body of knowledge, a library of procedures, a set of tools, a memory, and a policy that says where its autonomy stops.

Every term below is defined here or on part one. You do not have to run the simulation to follow any of it: the same twenty steps are written out in the walkthrough underneath it, and each component is explained in the anatomy section after that — though with JavaScript on, the component definitions open one at a time when you select one.

One autonomous task, start to finish

You give one instruction — “upgrade the payments SDK to v3 and ship it” — and leave. Twenty steps later there is a deployed release, one corrected mistake, and exactly one interruption.     What an agent is composed of

    Eight parts. Two of them — the model and the harness — are part one's subject and are referenced here rather than re-taught. The other six are what turn a loop into an agent.

    Select a component above to read what it does. All eight definitions are printed below when JavaScript is off.

    Model

    A large language model behind an API: text in, text out, no memory between calls and no side effects. It decides what to ask for; it never does anything itself.

    Architectural role: a stateless third-party dependency. Taken apart in part one.

    Harness

    The ordinary program around the model: it builds the context window, makes the HTTP call, parses the reply, executes tool calls, and runs the loop until the work is done.

    Architectural role: the whole control plane. Everything else on this page is something the harness loads, enforces or executes. See Inside the harness.

    Identity

    The always-resident instructions that say who this agent is: its role, its tone, its hard rules, its refusals. Technically it is a system prompt — the thing part one showed sitting at the front of every request.

    Architectural role: the one knowledge layer that is never evicted, so it is also the most expensive per token — you pay for it on every single model call of every run.

    Semantic layer

    The agent's structured knowledge about this domain: repository conventions, architecture notes, domain vocabulary, the rules that are true regardless of today's task. It is what turns a general assistant into one that knows your system.

    Architectural role: a tiered cache over a knowledge base. Some tiers are always resident, some are fetched on demand, some are evictable — because context, not storage, is the scarce resource.

    Skills

    Named, packaged procedures: a piece of metadata saying when the skill applies, plus instructions for carrying it out. “Upgrade a dependency” or “triage a failing build” are skills. They sit on disk until a task matches one.

    Architectural role: lazily loaded procedure library. Adding the hundredth skill costs nothing at run time, because only the matching one is ever read into context.

    Tools

    The functions the harness is willing to execute on the model's behalf: read a file, run a command, call an API. The registry of what exists, and the schemas for calling it.

    Architectural role: the agent's only means of affecting anything real, and therefore its entire blast radius. Covered in part one.

    Memory

    Durable notes carried between runs — what was learned, what went wrong last time, what the user prefers. Stored outside the context window and retrieved by relevance when a new task starts.

    Architectural role: a retrieval store, not a context tier. Recall is a search problem: everything written must be worth re-reading, or memory becomes noise that crowds out the task.

    Permission policy

    The rules that classify actions: allowed outright, allowed with a record, or requiring a human's approval before the harness will execute them.

    Architectural role: the boundary of autonomy, and the one component the model cannot argue with. It is enforced in the harness before execution, so a persuaded or mistaken model still cannot cross it.

    The semantic layer, and why it is layered

    An agent's knowledge is not one bag of text. It is tiered, and the tiers differ in exactly one respect that matters: when they get loaded into the context window, and when they leave.

    The reason is part one's cost fact. Every iteration re-sends the whole context window, and cost and latency scale with its size. A megabyte of documentation the agent could consult is free while it sits on disk and expensive the moment it is loaded — expensive on this call and on every call after it, because the context is append-only within a run. So the design question is never “what might be useful?” but “what is worth paying for on every remaining model call of this run?”

    Identityalways loaded
    Role, rules, refusals. Present from the first call to the last, never evicted. Keep it short: you pay for it every time.
    Tool definitionsalways loaded
    Every callable function's name, description and argument schema. Resident for the same reason identity is: the model can only ask for a tool it can currently see described. Adding tools costs context on every call, which is why large agents scope their registry per task.
    Project knowledgeloaded once per run
    Conventions, architecture, domain vocabulary — true of this system regardless of task. Loaded at the start and kept, because nearly every step needs it.
    Skill instructionsloaded on request
    Two things, on two different rules. Every skill's description is always resident — a name and a trigger line each, cheap enough to carry the whole library. The instructions are not: they load only after the model, reading those descriptions during a call, asks for one by name. So a skill can never load before the first model call, and the matching is the model's judgement, not a lookup the harness performs. Instructions are dropped when the work is done; the descriptions stay.
    Recalled memoryretrieved by relevance
    Notes from earlier runs, fetched by search rather than loaded wholesale. A handful of lines, chosen because they match the task at hand.
    Working transcriptgrows, then compacts
    The plan, the tool calls and their results. The only tier that grows without bound, and therefore the first thing compacted: superseded output is replaced by a short summary of what it established.

    How these tiers map to the eight components. Four of the components are tiers: identity, the tool registry (whose definitions are resident all run), the semantic layer (which supplies the project-knowledge tier) and skills. Memory is a tier's source rather than a tier itself — it lives outside the context window and only the handful of notes it returns are loaded. The rest never enter the context as knowledge at all: the model and the harness are the machinery that reads and assembles it, tool execution produces the working transcript, and the permission policy is enforced in code before execution and is never something the model reads.

    The architect's version: this is a cache hierarchy. Identity is pinned; project knowledge is loaded on run start; skills are demand-paged on match; the working transcript is the evictable region. Compaction is eviction with a lossy summary in place of the discarded pages — and like any lossy cache, what it drops is a design decision you should make deliberately rather than discover in production.

    Anatomy of a project-context file

    The semantic layer is files too. Where a skill packages a procedure, a project-context file packages facts that stay true — the things a newcomer would need told once and would then apply to every task.

    ---
name: payments-service
scope: always            # loaded at the start of every run in this repo
tokens: ~1500
---

- Money is integer minor units. Never floats, anywhere.
- Every outbound call is idempotent; retries are safe by construction.
- The webhook signer is the fragile part. Changes there need a smoke check.
- Deploys are approval-gated in production, automatic in staging.

    scope is the loading rule. always pins this file for the whole run; a file scoped to a path or a topic would instead be fetched only when the task touches it. That single field is the difference between a tier you pay for on every model call and one you pay for occasionally.

    Relevance is decided before loading, not after. Note the third line: it is why the agent in the simulation recalled the webhook signer at all. Knowledge that never gets selected may as well not exist, so what earns a place in an always-loaded file is a real budget decision — every line here is charged against the context budget on every single call of every run.

    Anatomy of a skill

    A skill is a file. The top half is metadata that lets the harness decide whether to load it; the bottom half is instructions the model follows once it has been loaded. Nothing about it is magic — it is a procedure written down, with a trigger attached.

    ---
name: dependency-upgrade
description: Upgrade a third-party package across a repo and verify it
when_to_use: task mentions upgrading, bumping or migrating a dependency
allowed_tools: [read_file, edit_file, run_tests, run_shell, deploy]
---

1. Find every call site before changing anything.
2. Read the target version's migration notes.
3. Apply changes file by file; keep each edit reviewable.
4. Run the full test suite. If it fails, diagnose before editing again.
5. Never deploy without an explicit approval step.
6. Smoke-check the health endpoint after deploying.

    The metadata is the load decision, and the model makes it. The name and when_to_use lines are in the context from the start — that is the whole catalog, and it is what the model reads, during a call, to decide this skill applies. It then asks for it by name and the harness fetches the body. allowed_tools narrows what the procedure may reach for even if the agent has more tools available. The file's body costs nothing until that request is made, which is why it cannot be loaded before the first call.

    The instructions are ordinary prose. They are not code and they are not enforced: step 5 is a strong instruction to the model, not a guarantee. The guarantee lives in the permission policy, which stops the deployment whether or not the skill remembered to mention it. That distinction — instruction versus enforcement — is the one to hold on to.

    What “autonomous” actually claimed

    Twenty steps ran with nobody watching. That is the real claim, and it is worth stating precisely, because the word does a lot of unearned work in product copy.

    Autonomous means no human between iterations. The agent planned, loaded what it needed, edited, tested, failed a test, diagnosed the failure, fixed it and re-tested — without asking. The self-correction at steps 9–12 is the whole value proposition: a system that stops at the first failure needs a human per failure, which is not autonomy, it is a slower kind of supervision.

    Everything the tools returned was untrusted. At steps 9 and 10 the agent read a failing test's output and acted on it. That output is text the agent did not write, arriving through a tool result — the inbound half of the trust boundary from part one. A file, a web page or a build log can carry instructions, and an agent running unattended is precisely the case with nobody reading them first. This is why the permission gate has to be enforced in the harness: it is the one control that still holds when the model has been convinced by something it read.

    Autonomous does not mean unbounded. At step 14 the agent tried to deploy, and stopped — not because the model chose caution, and not because the skill file said to. It stopped because the permission policy classifies production deployment as approval-required, and the harness checks that classification before executing, every time. A model that had been talked into deploying, or that had simply misjudged, would have hit exactly the same wall.

    What happens when the answer is no. A denial is not an exception either — it comes back as a result, exactly like a failed test. The agent reads it, and either adapts (deploy to staging instead, open a change request, describe what it would have done) or stops and reports that it cannot finish. Suspension is real suspension: the loop is not running and no tokens are being spent while it waits, so a gate can sit unanswered for a day without costing anything. What it does mean is that the run now has a human in its critical path, which is exactly the trade you chose when you classified the action.

    Two ceilings you also have to set. The self-correction loop that fixed the failing test is the same machinery that will retry a hopeless command forever, so the harness imposes an iteration ceiling and a token or cost budget for the run. Neither is a safety feature in the permission sense; both are there because an agent that cannot succeed does not necessarily notice.

    When the context fills anyway. Compaction buys room, but it is lossy and it only buys so much. The standard next answer is delegation: hand a well-scoped sub-task to a fresh agent with its own context window, and take back only the result. That keeps the parent's context small at the cost of the sub-agent seeing less. It is a large topic and this page does not cover it further — the point here is only that it is the usual response to context pressure, not an exotic one.

    That is the line to hold when someone asks how much autonomy to grant: you are not tuning how much you trust the model's judgement. You are choosing which actions the harness will execute without asking — a policy decision, written in your code, enforced regardless of what the model says.

    Glossary — the additions

    Part one's glossary covers token, context window, system prompt, tool call, agentic loop, sandbox and the rest. These are the terms this page adds.

    Agent
    A harness and model, plus the identity, semantic layer, skills, tools, memory and permission policy that let it pursue a multi-step task rather than answer a single question.
    Identity
    The always-resident instructions defining an agent's role, tone and hard rules. Implemented as a system prompt; distinguished by the fact that it is never evicted.
    Semantic layer
    The agent's structured knowledge of a specific domain or codebase, organised into tiers that differ in when they are loaded into context and when they are dropped.
    Skill
    A named, packaged procedure: metadata declaring when it applies, plus instructions for carrying it out. Loaded into context only when a task matches its trigger.
    Just-in-time loading
    Reading knowledge into the context window at the moment it becomes relevant instead of up front, so unused knowledge costs nothing.
    Memory
    Durable notes kept outside the context window between runs and retrieved by relevance at the start of a new task.
    Compaction
    Replacing superseded parts of the working transcript with a shorter summary so the context window stops growing. Lossy by definition.
    Context budget
    The share of the context window a run can afford to spend on each tier of knowledge, given that everything loaded is re-sent on every model call. The constraint that makes tiering necessary in the first place.
    Permission policy
    Rules classifying actions as allowed, allowed-with-record, or approval-required, enforced by the harness before execution. The boundary of an agent's autonomy.
    Permission gate
    The point where the policy suspends the loop and waits for a human decision before a classified action may run.
    Self-correction
    Feeding a failure — a failed test, an error result — back into context as input, so the agent diagnoses and retries instead of halting.
