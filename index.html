How AI Harnesses Work

The model writes the words. Everything else — building the prompt, running the tools, looping until the job is done — is the harness. Watch one turn happen, piece by piece.

When you chat with an AI coding agent or assistant, you're never talking to a language model directly. You're talking to a harness: the software wrapped around the model. The harness assembles everything the model sees, executes everything the model asks for, and repeats that loop until your request is finished. The model is the brain; the harness is the hands.

Four players are involved in every turn: the User who asks, the Harness that orchestrates, the Model API that reads and writes text, and the Tools & Environment — files, shells, and services the harness can operate on the model's behalf.

    Anatomy of the context window

    A language model is stateless: it remembers nothing between calls. So on every single call, the harness rebuilds the model's entire world from scratch — one long stack of text called the context window. "Memory" in a chat is an illusion the harness maintains by replaying the whole conversation every time.

    The stack is append-only during a turn. Each tool call, each result, each answer gets added to the bottom, and the whole thing is re-sent on the next call. That's why long sessions get slower and more expensive, and why every harness eventually has to summarize or trim old history: the window has a hard token limit.

    Anatomy of a tool call

    // The model's entire output — just structured text:
{
  "type": "tool_use",
  "name": "list_files",
  "input": { "path": "." }
}

    The model only writes this request. It has no access to your files, network, or shell — it produced a piece of JSON and stopped.

    // The harness executes it and appends the result:
{
  "type": "tool_result",
  "content": "index.html\nREADME.md\nsrc/\ntests/ …"
}

    The harness does everything real: it validates the request against the tool's schema, checks permissions (maybe asking you first), runs the actual command, and feeds the output back into the context as a new message. Then it calls the model again — that's the agentic loop.

    What happens when a tool fails

    Failure is part of the loop, not an exception to it. If validation rejects the arguments, a permission check denies the call, or the command itself errors out, the harness doesn't abandon the turn — it writes the failure into a tool_result marked as an error and sends it back like any other result. The model reads that error and adapts: correcting a bad path, reaching for a different tool, or telling you plainly why it can't proceed. A turn that looks like it "just worked" has often absorbed two or three failures on the way.

    Real harnesses layer more machinery on top of the basic loop. They truncate oversized output, so reading one enormous file can't swallow the whole context window. They handle several tool calls from a single model response, sometimes running independent ones in parallel. They stream the model's text back to you as it arrives instead of waiting for the full reply. And they retry transient API failures rather than surfacing every hiccup to you.

    Inside the harness

    Everything above describes the harness from the outside. Underneath, it is an ordinary program — a loop, a lookup table, a subprocess call and an HTTP client. Here is that program, reduced to its load-bearing parts, and the five components it decomposes into.

    Three terms recur below, and nothing else here is specialised vocabulary. A token is the unit of text the model is billed and limited by, roughly three-quarters of an English word. The context window is the single block of text sent with each request, capped at some maximum number of tokens. The system prompt is the standing instruction text the harness puts at the front of that block.

    1 · The trust boundary sits at the model API

    Everything the model emits — tool names, arguments, file paths — is untrusted data until the harness validates it. Treat it exactly as you would treat a request arriving from an anonymous client.

    The boundary runs both ways, and this is the half that surprises people. Untrusted content also enters through tool results: file contents, command output, web pages, ticket text. Once appended, that text sits in the same context as your instructions, and the model may act on words it finds there — an instruction hidden in a fetched page can become a tool call. This is indirect prompt injection, and it is why the permission check has to be the thing that stops a dangerous action, not the model's judgement about whether to request one.

    2 · Model calls dominate cost and latency, and both scale with context size

    Every iteration re-sends the entire context window, and each resend is larger than the last: a request that makes six tool calls costs seven model calls, over a transcript that grows at every step.

    Providers bill cached input at a fraction of the normal rate, but caching only applies to a stable prefix — which is why the assembler puts the system prompt and tool definitions first and never edits them. Reordering that prefix silently multiplies the bill. Tool execution is often milliseconds, though unbounded without a timeout; the model call is reliably seconds. Context size is the cost lever.

    3 · Security, observability and spend controls can only live in the harness

    The model cannot enforce a permission, emit a metric, or stop at a budget — it has no side effects at all. Every guardrail, every log line and every limit is something you build on this side of the boundary.

    The loop, as code

    Generic pseudocode — no particular product or SDK. Hover or tap a line to see which component owns it; opening a component highlights its lines.

    
          context = assemble(systemPrompt, toolDefs, history, userMessage)
          iterations = 0
          
          while (true) {
              context = compact(context, BUDGET)    // evict when full
              reply   = modelApi.send(context)      // one HTTP call
              context.append(reply)                 // append-only
          
              // a reply may hold text AND tool calls
              if (reply.toolCalls.isEmpty())
                  return reply.text                 // plain answer: done
          
              for (call in reply.toolCalls) {
                  try {
                      tool = registry.lookup(call.name)  // unknown -> error
                      args = validate(call.input, tool.schema)
                      requirePermission(tool, args)      // may ask the user
                      out  = sandbox.run(tool, args, TIMEOUT)
                  } catch { out = asError(...) }        // failure is data
                  out = truncate(out, MAX_OUTPUT)       // cap the output
                  context.append(result(call.id, out))  // untrusted input
              }
          
              if (++iterations >= MAX_ITERATIONS)
                  return abort("iteration ceiling")     // stop condition
          }

    What this reduction leaves out: streaming the reply as it arrives, retries and backoff around the API call, executing independent tool calls in parallel rather than in sequence, the approval interface behind requirePermission, and delegating sub-tasks to nested harnesses. Each is real and each is orthogonal to the control flow shown here.

    The five subsystems

    ▸Context assemblerlines 1, 5, 7, 21

    Job: build the block of text that goes into every request — system prompt, tool definitions, conversation history, newest message — and decide what to drop when it stops fitting.

    This is where cost and latency are actually determined, because the block is rebuilt and re-sent on every iteration and its size multiplies across the loop. Keeping the stable parts first (system prompt, then tool definitions) is what lets the provider serve a cached prefix, so the assembler's ordering is a billing decision as much as a formatting one. It is append-only within an iteration, which makes it auditable: the exact bytes sent can be logged verbatim. When the budget is exceeded something must be evicted, and what goes — oldest messages, largest tool results, or a summary standing in for both — is a product decision with no correct default.

    Done badly: sessions that get vaguer the longer they run, because the assembler quietly dropped the instructions that mattered while keeping recent chatter.

    In the simulation: step 3, step 5, step 10, step 12

    ▸Tool registry & validationlines 15–16

    Job: hold the catalogue of callable functions with their argument schemas, and reject anything requested that does not match one.

    This is the enforcement point for the trust boundary. A name that is not in the registry does not exist, no matter how confidently it was requested, and schema validation here is not a formality — it is the same input validation you would write for a public HTTP endpoint, because functionally that is what this is. Rejections happen inside the same try as execution, so they come back as ordinary results the model can correct itself from rather than aborting the run.

    Done badly: a tool invoked with arguments nobody checked, and a stack trace from three layers down surfacing to the user as the assistant's answer.

    In the simulation: step 7 — this component owns the validation half of that step.

    ▸Executor & sandboxlines 14, 17–20

    Job: actually run the requested tool under a permission check, a time limit and an output cap — and turn any failure into data.

    This is the only component with real side effects, so it is where blast radius is decided. It runs with some identity and some filesystem and network reach, and whatever those are is exactly what a mistaken or manipulated call can touch. Timeouts and output caps are containment rather than politeness: an unbounded command holds the loop open indefinitely, and unbounded output consumes the very budget the assembler is trying to manage. Note what the try encloses — lookup, validation and permission failures are captured on the same path as a crashing command, so none of them can end the run.

    Done badly: a typo'd deletion running with the service's own privileges — or one verbose command whose output fills the context window and derails everything after it.

    In the simulation: step 7, step 8, step 9 — this component owns the permission half of step 7.

    ▸Model API clientline 6

    Job: make the HTTP request to the model service and hand back a parsed reply.

    One line in the loop, and almost all of the wall-clock time and nearly all of the bill. It is a network call to a third party, so it inherits every concern you would apply to any external dependency: timeouts, retries with backoff, rate-limit handling, and a circuit breaker for when the service degrades. It is also the natural instrumentation point — request size, response size, latency and cost per call all pass through here, and if you do not measure them here you will not measure them at all.

    Done badly: a run that hangs forever because one upstream request had no timeout, or a bill nobody can attribute because per-call sizes were never recorded.

    In the simulation: step 4, step 6, step 11, step 13

    ▸Loop controllerlines 2, 4, 9–11, 13, 22, 24–26

    Job: decide whether to go round again, and guarantee that the loop always ends.

    The only natural exit is a reply containing no tool call, and that is a decision made by a non-deterministic remote service — which means it is not a guarantee. Every other stop condition is one you impose: an iteration ceiling, a token budget, a wall-clock deadline, a repeated-call detector. This component owns the state machine for the whole request, so cancellation and resumption belong here too. Treat “the model will stop on its own” as a happy path, not as a design.

    Done badly: an agent that loops on the same failing command until somebody notices the spend graph.

    In the simulation: step 11, step 12, step 13

    Glossary

    Harness
    The software around the model: it builds the context, calls the model API, executes tool calls, enforces permissions, and loops until the turn is done. Also called an agent framework or scaffold.
    Model (LLM)
    A large language model behind an API. Text in, text out — and nothing else: no memory of earlier calls, no side effects, no hands, no network. Its output is sampled rather than computed, so the same input can come back worded differently each time.
    Token
    The unit models read and write — roughly ¾ of an English word. Context limits, costs, and speed are all measured in tokens.
    Context window
    The complete stack of text the model sees on one call: system prompt, tool definitions, and conversation so far. Capped at a hard token limit.
    System prompt
    Instructions the harness places first in the context: role, rules, style, environment details. The user usually never sees it.
    Tool call
    A structured request the model writes (a name plus JSON arguments) asking the harness to do something in the real world.
    Agentic loop
    The cycle the harness runs: call model → if it requested a tool, execute it, append the result, call again → repeat until the model answers in plain text.
    Sandbox
    The restricted environment a tool runs in — limited filesystem reach, network access, privileges and time. It is what decides how much damage a mistaken or manipulated tool call can do.
    Blast radius
    How far the damage spreads when something goes wrong. For a harness it is set by the executor's identity and permissions, not by anything the model does.
    Compaction (eviction)
    Dropping or summarising older parts of the context window once it no longer fits the token limit. Eviction is the discarding; compaction usually means replacing a long stretch with a shorter summary of it.
    Circuit breaker
    A standard resilience pattern: after repeated failures from a dependency, stop calling it for a while instead of retrying into a wall. Applied here to the model API client.
    Iteration ceiling
    A hard cap on how many times the loop may go round for a single user request, imposed by the harness so the run always terminates even if the model never stops asking for tools.
    Indirect prompt injection
    Instructions planted in content the model reads through a tool result — a file, a web page, a ticket — which the model may then act on as if you had written them.

    Common misconceptions

    • "The AI ran a command on my machine."
      The model wrote a request; the harness ran the command. Sandboxing, permission prompts, and allowlists all live in the harness — which is exactly why harness design matters for safety.
    • "It remembers our conversation."
      The model forgets everything after each call. The harness re-sends the whole history every time, and may summarize old parts when the window fills up.
    • "It's thinking while the tool runs."
      During a call the model really is working — many models spend hundreds of "thinking" tokens reasoning before they commit to an answer. But between calls it doesn't exist as a running process at all. The harness executes the tool while nothing on the model side is running, then wakes the model up with a bigger context.
